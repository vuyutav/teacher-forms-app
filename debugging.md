# Debugging & Project Health Guide 🛠️

This document outlines current issues, potential production risks, and architectural weaknesses discovered in **Fontaine Forms**, along with their recommended solutions.

---

## 1. Critical Backend Issues

### ❌ Hardcoded Localhost in Frontend
- **Problem:** In `frontend/lib/api.ts`, the `getPublicForm` function uses a hardcoded `http://localhost:5000` URL.
- **Impact:** When deployed to production (Vercel/Netlify), students will be unable to view forms because their browsers will try to connect to their own local machine instead of the production server.
- **Solution:**
  ```typescript
  // Change this:
  export async function getPublicForm(formId: string) {
    const res = await fetch(`http://localhost:5000/api/public/forms/${formId}`)
    return res.json()
  }

  // To this:
  export async function getPublicForm(formId: string) {
    const res = await fetch(`${API_URL}/api/public/forms/${formId}`)
    return res.json()
  }
  ```

### ❌ Missing Production Database Migrations
- **Problem:** The project uses `db.create_all()` (implied or manual) but lacks a migration tool like **Flask-Migrate**.
- **Impact:** Adding new columns to tables in the future will be difficult and risky on production (Supabase). You might lose data if you have to drop and recreate tables.
- **Solution:**
  1. Install Flask-Migrate: `pip install Flask-Migrate`
  2. Initialize in `app.py`:
     ```python
     from flask_migrate import Migrate
     migrate = Migrate(app, db)
     ```
  3. Use `flask db migrate` and `flask db upgrade` to manage changes.

## 2. Potential Production Risks

### ⚠️ Fallback JWT Secret
- **Problem:** `backend/config.py` uses `'fallback-secret'` if `JWT_SECRET_KEY` is missing.
- **Impact:** If the environment variable isn't set in production, your application is insecure. Anyone could forge tokens.
- **Solution:** Remove the fallback in production code.
  ```python
  # Better approach:
  JWT_SECRET_KEY = os.environ['JWT_SECRET_KEY'] # Raises error if missing
  ```

### ⚠️ Permissive CORS Policy
- **Problem:** `backend/app.py` defaults to `*` for origins if `ALLOWED_ORIGINS` is not set.
- **Impact:** While convenient for development, a wide-open CORS policy can be a security risk.
- **Solution:** Ensure `ALLOWED_ORIGINS` is strictly set to your production frontend URL in the Render/Netlify dashboard.

## 3. Frontend & UX Improvements

### 🔍 Brittle API Error Handling
- **Problem:** Most functions in `lib/api.ts` return `res.json()` directly without checking if `res.ok` is true.
- **Impact:** If the server returns a 500 or 401 error, the frontend might crash or show "Undefined" instead of a helpful error message.
- **Solution:** Wrap fetch calls in a helper that checks for status codes.
  ```typescript
  async function apiFetch(url: string, options: RequestInit) {
    const res = await fetch(url, options);
    const data = await res.json();
    if (!res.ok) throw new Error(data.error || 'Something went wrong');
    return data;
  }
  ```

### 🔍 Deployment Documentation Conflict
- **Problem:** `README.md` mentions **Render**, but the root directory contains `netlify.toml` and **Mangum** (Netlify/AWS Lambda adapter).
- **Impact:** New developers will be confused about where the backend is actually supposed to live.
- **Solution:** Standardize the documentation. If using Netlify Functions, remove Render mentions. If using Render, remove `netlify.toml` and clarify that Mangum is optional.

## 4. Maintenance & Scalability

### 🧩 Type Safety "Holes"
- **Problem:** `lib/api.ts` uses `object` for payloads (e.g., `updateForm(id, data: object)`).
- **Impact:** TypeScript won't warn you if you send the wrong keys to the API, leading to "Bad Request" errors that are hard to track.
- **Solution:** Define Interfaces:
  ```typescript
  interface QuestionPayload {
    question_text: string;
    question_type: 'text' | 'multiple_choice' | 'checkbox' | 'dropdown';
    options?: string[];
  }
  ```

### 🧩 Lack of Automated Testing
- **Problem:** No `tests/` directory found.
- **Impact:** Small changes in the backend might accidentally break the frontend without anyone noticing until a user reports it.
- **Solution:** Add basic unit tests for the Auth routes using `pytest` to ensure login/register logic stays solid.
